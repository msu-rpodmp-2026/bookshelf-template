# BookShelf — проект курса «Разработка ПО для мобильных платформ»

Это ваш личный репозиторий на весь семестр. В нём постепенно вырастает
приложение **BookShelf** — электронная картотека личной библиотеки.

Проект **накопительный**: каждая лабораторная работа добавляет к нему одну
возможность. Код не переписывается заново — он накапливается. Занятия 1–5
создают консольный прототип на Dart, занятия 6–13 превращают его в мобильное
приложение на Flutter.

## Как сдаётся работа

Каждая лабораторная работа сдаётся **отдельной веткой и pull request**.

```
main                    ← защищена: изменения попадают только через PR
 ├── lab-01  →  PR «ЛР №1. Установка Dart SDK. Типы данных»
 ├── lab-02  →  PR «ЛР №2. Управление потоком и функции»
 ⋮
 └── lab-13  →  PR «ЛР №13. Архитектура и защита проекта»
```

Порядок действий — в [docs/git.md](docs/git.md). Коротко:

```bash
git switch main && git pull
git switch -c lab-04
# ... работа над заданием ...
git add .
git commit -m "ЛР №4: сохранение каталога в JSON"
git push -u origin lab-04
```

Дальше на GitHub нажать **Compare & pull request**, заполнить появившийся
шаблон и отправить.

### Репозиторий публичный

Ваш репозиторий виден всем, включая однокурсников. Это сделано осознанно:
к концу семестра у вас остаётся публичный проект с историей из тринадцати
pull request — то, что имеет смысл показывать работодателю. После сессии он
никуда не девается.

Обратная сторона: чужой код тоже виден. Копировать его бессмысленно и
рискованно. Задание у всех одно, поэтому решения похожи и без копирования —
но даты коммитов показывают, кто написал раньше, а на защите нужно объяснить
каждую строчку. Подставляете при этом не только себя, но и того, у кого взяли.

Не храните в репозитории ничего личного: он открыт.

### Правила

1. **Ветка отводится от актуального `main`.** То есть после того, как
   предыдущая работа принята и влита. Если ЛР №3 ещё не принята, начинать
   ЛР №4 рано.
2. **Имя ветки** — строго `lab-01` … `lab-13`.
3. **Заголовок PR** — `ЛР №N. Тема работы`.
4. **Напрямую в `main` не пушим.** Ветка защищена, push будет отклонён.
5. **Коммитов должно быть несколько**, с осмысленными сообщениями.
   Один коммит «сделал всё» накануне срока — это видно, и это минус.
6. **Отчёт сдаётся в Moodle**, как обычно. В репозитории — только код.

### Автоматическая проверка

Каждый pull request проверяется автоматически: форматирование
(`dart format`), статический анализ (`dart analyze` / `flutter analyze`) и
тесты, если они есть.

**Красная галочка — работа к проверке не принимается.** Исправьте и запушьте
в ту же ветку: проверка запустится заново, PR обновится сам, заново открывать
его не нужно.

Проверить всё то же самое у себя до отправки:

```bash
dart format .
flutter analyze
flutter test
```

### Как принимается работа

| Состояние PR | Что это значит |
|---|---|
| Проверка красная | К ревью не принимается, исправляйте |
| Проверка зелёная | Ждёт ревью преподавателя |
| **Changes requested** | Есть замечания — прочитайте комментарии и доработайте в той же ветке |
| **Approved** + merge | Работа принята. Дата merge — дата сдачи |

## Структура репозитория

```
bookshelf_console/    проект занятий 1–5 (создаётся в ЛР №1)
bookshelf/            проект занятий 6–13 (создаётся в ЛР №6)
docs/git.md           памятка по работе с git
```

Каталоги проектов вы создаёте сами по ходу курса — командами
`dart create bookshelf_console` и `flutter create bookshelf`.

> PR к ЛР №6 будет очень большим, на две сотни файлов. Это нормально:
> `flutter create` генерирует каркасы для Android и iOS. Пугаться не нужно.
